# Spec

1. 新 PDF 解析优先使用纯文字页的有效文字层。无可用文字的页（包括只有矢量图形的页）与实际绘制图片的混合页进入完整 OCR，保留旧混合页中图片文字，不拼接重复文字、不跳页。扫描件继续受控 OCR。
2. 新算法使用新解析身份，旧已保存的原件、解析页、索引身份和引用保持。三份失败 PDF 通过现有同资料原件更新形成新 revision，保留旧失败任务；不能篡改旧 parser_revision 或直接重试不兼容 claim。
3. 解析时间继续有界，但允许配置足以处理多页扫描件的总期限；生产值依据实际受控解析验证设置，不以无限等待或截页代替成功。
4. 空清理队列扫描不得取得全库维护锁；实际清理仍须独占维护栅栏、重新校验及原子 claim。不得放宽删除、保留依据或绕过维护隔离。
5. 资料访问故障与模型故障分开验证。只读可用性检查不触发模型。真实上传自动索引单独统计请求，不挪用旧 halted 预算、不自动重试失败模型请求。
6. 发布保持 schema、模型/检索/认证配置、成功资料及原件不变；先备份与核对运行账户可读，再切换可回滚包，不用旧数据库覆盖新业务数据。旧全仓失败如仍存在须原样记录。

## 指定 OCR 模型（2026-10-10）

7. 扫描识别选择硅基流动 `PaddlePaddle/PaddleOCR-VL-1.5`。服务商、标准 OpenAI 兼容地址和模型配置与业务解析逻辑分离；不在源码写凭据，不借用视觉描述/caption 作为 OCR 正文。
8. [PaddleOCR 官方接入说明](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md#32-client-usage-methods)明确支持该服务商/型号，同时区分版面分析及 VLM 识别。完整文档方案采用版面分析、区域识别和阅读顺序恢复；不能把一次整页 chat 请求宣称为完整 PaddleOCR 解析流水线。部署前验证额外依赖与实际资源消耗，不能在未核对容量时直接加重生产负载。
9. PDF 页级文字使用独立小 Interface；原页号、页序和原件身份由服务端保留，模型不能生成可信定位。不能把纯文字或 Markdown 响应装成带真实词框的 `ParsedImage`。独立图片和视频现有 OCR 词框合同暂不改。
10. 文字层、扫描页与图文混合页分别验证。OCR 调用另记本批请求，不续用旧 halted 余额、不自动重试；保留解析失败与索引失败的区别。云请求的凭据传递和固定字段计数须纳入实际 worker 链路，不能因子进程丢弃 stderr 漏计请求。

### 接线决定

- Java 仍为资料业务权威；PDF worker 经本机 Unix socket 调用独立 OCR 解析进程。后者只做版面/区域识别/页级文字，不接数据库或公开 HTTP 路由。
- 内部协议使用 4 字节大端长度及 UTF-8 JSON，请求绑定 `version=1`、UUID `request_id`、固定 `profile`、总期限、PNG 原图；成功响应复验同一 ID/profile 和全文，失败固定原因码，不把失败当空页。
- 首版 profile 为 `paddleocr-vl-1.5-pipeline-v1`，socket 私有权限，云凭据仅进入 OCR 进程私密配置，不在 Java 参数或 Git 中传递。OpenAI 兼容云端调用由独立 Adapter 执行并记录固定字段请求计数。
- 保留本地 Tesseract Adapter 和旧版本读取；Python 仅为官方 Paddle 推理依赖的隔离工作进程，不迁移 Java 业务。默认不启用新路径，生产启用须先实际资源、完整页和旧来源回读验证。
