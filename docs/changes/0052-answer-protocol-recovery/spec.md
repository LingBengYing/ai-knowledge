# Spec

1. 先准确区分实际模型处理失败阶段。诊断仅固定operation/phase/reason枚举、finish_reason白名单和数字长度/usage；不得记录问题、候选、模型正文、凭据、任意错误字符串或原始Throwable。
2. 观测补丁不改变请求体、模型选择、既有错误返回、原文校验或索引身份。对已确认根因再作最小修复；不得猜测并放宽grounding，HTTP200不作语义成功证据。
3. 以原失败模式的确定性红→绿验证修复，保留现有正反例，再在20次共同额度内进行完整“检索→摘录→综合→核验→引用回读”。
4. 保留旧失败结果；实际调用前记账，同问题/同构建不自动重发，不超预算。真实失败先停止该链并检查原因，只有已落实修复后才启动下一验收步骤。
5. 仅受影响后端修复可发布；前端、当前活动模型v6、schema29、10份资料及索引保持。原75.64%覆盖率缺口和PDF启动竞态风险不抹去、不改阈值，旧一次性发布例外不冒称完整门禁通过；新的发布决定与验证证据单独记录。

## 本轮真实根因后的最小修复

**最新用户决定覆盖下方中间8192方案**：“为啥有token上限，把上限去掉啊”。所有本次文字问答生成入口（通用/主题/知识/事实摘录、综合、核验）均不再发送max_tokens或max_completion_tokens，使用所选服务商默认输出预算。不能宣称消除了服务商自身的上下文/生成硬上限。原JSON/长度/原文校验及length拒绝保持，本批HTTP次数预算仍20。先确定性红绿验证；未部署前不称线上已生效。

有观测复现已确认extract的2048 token总输出预算耗尽（1955 reasoning），响应length被拒绝。采用供应商中立的标准`max_tokens`：摘录与同类结构化核验统一8192，综合16384保持；不添加供应商专属thinking开关，不更换模型，不改变PROMPT或索引revision。既有条数、字符数、JSON/原文校验及finish_reason必须stop的规则保持；更高输出预算不是允许接收截断结果，也不增加自动重试。

以上8192为已验证中间版本的历史，不再是最终交付合同。

## 第二阻塞：主题摘录与准入合同不一致

预算修复后的唯一灯塔复验，extract已validated/stop，随后incomplete_evidence且未综合。代码的主题路径中该码唯一可达条件是某条摘录缺少完整主题锚点；不能据此推断具体摘录正文。修复不放宽TopicEvidence、不丢弃失败摘录、不跨来源借主体：新增显式extractTopic调用及独立主题摘录提示，要求每条连续完整原文含完整主题、保留完整句/字段和条件，最多32条各1200码点。不动旧通用/事实/知识摘录提示及索引revision，新提示版本计入答案policy。Service仍先完整问题分类，显式字段问题继续原路径，所有检索原context仍用于综合/核验反证。
