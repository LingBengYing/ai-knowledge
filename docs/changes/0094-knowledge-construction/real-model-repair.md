# 真实模型验收发现与增量合同修复

2026-10-25，负责人已授权本版推送、生产发布并完成真实模型的批次建设及增量更新验收。本记录保留实际发现，不以 HTTP 成功或替身通过替代内容验收。

## 首次真实结果

两份本轮新合成 TXT 自动解析、嵌入并正式发布成功；DeepSeek 生成知识页 v1，经实际浏览器审阅采纳。仅替换其中一份资料后，自动索引、来源变化识别和增量提案生成成功。累计 5 次 HTTP（硅基流动嵌入 3、DeepSeek 编译 2）均成功，未发生传输重试。

人工审阅发现 v2 提案重复了未变章节：v1 概述同时引用两份资料，因此受影响概述需要两份资料上下文。旧实现把这些输入交给整页编译，模型生成了完整的三个章节，再追加原有未变章节，造成重复。问题提案已在页面“暂不采纳”，正式知识页保持 v1；原验收状态、提案和请求审计保留，标记为语义失败并停止后续调用。

## 修复合同

- 增量编译使用独立 `revise_wiki` 操作，OpenAI 兼容 HTTP 协议保持不变，仍为单次模型请求。
- 输入列明每个受影响章节的原编号、标题、正文及该章节允许使用的当前证据；需要多份资料上下文的章节仍保留该上下文。
- 输出必须对每个目标章节返回且仅返回一次；未知、遗漏、重复编号或越界来源拒绝，不按具体标题、样本文本或相似度猜测去重。
- 服务端按原编号和原顺序替换受影响章节；未变章节的编号、正文和来源完整保留。资料版本检查、并发采纳检查与人工审阅保持。
- 不改变数据库 schema、公开 HTTP API、原件、旧资料、索引、前端或模型配置。

## 续验边界

在同一已授权发布任务内修复并部署 Java 补丁后，只针对已更新的这两份合成资料重新生成一次增量提案，不重新上传、解析或索引。原失败验收保持停止；续验独立保存单次提交标记和失败记录，并将新增请求与原 5 次统一核对。不得把原提案的 `compile_wiki validated` 当成新 `revise_wiki` 成功。
